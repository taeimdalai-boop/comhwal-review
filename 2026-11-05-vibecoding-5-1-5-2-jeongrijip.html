4. 딱 하나의 철칙 — "기획서(PLAN.md) 없으면 코드 안 쓴다"

🔑 강사 시그니처
"코드부터 치면 AI가 30분 헤맵니다. PLAN.md에 '뭘·왜·어떻게'를 3줄이라도 먼저 쓰고 시작하세요. 이게 바이브코딩 실력의 절반입니다."

왜 AI 시대에 기획이 더 중요한가? AI가 실행(코딩)을 거의 공짜로 해주니, 사람 사이의 차이는 "무엇을·왜·누구에게"를 얼마나 명확히 정의하느냐에서만 갈립니다. 좋은 기획서의 기준은 하나: "사람도 AI도 똑같이 이해하는가?"

기획 4종 세트 (통째로 AI에 전달)

문서답하는 질문예시 (관상 AI)
① PRD (제품요구서)왜·누구에게·무엇을첫인상 걱정하는 20대에게 관상 요약 제공
② 기능명세서무슨 기능을 어떻게사진 업로드 → AI 분석 → 요약 1줄 (최대 500토큰)
③ 유저플로우사용자가 어떻게 움직이나홈 → 업로드 → 로딩 → 결과카드 → 저장
④ 와이어프레임화면이 어떻게 생겼나결과카드: 위 사진, 아래 요약 1줄 + 저장 버튼

와이어프레임은 완벽한 디자인이 아니라 "위엔 제목, 가운데 업로드 버튼, 아래 결과 카드" 정도의 뼈대면 충분합니다. (참고: MCP = AI에 노션·GitHub 같은 외부 도구를 연결하는 표준 규격. 심화 주제)

5. 기획서 → 프론트 → 개발 (3단 파이프라인)

기획 4종 + 레퍼런스→Claude Design (화면)→Claude Code (API·DB·로직)→완성 v1
  1. 레퍼런스로 시작 — 닮고 싶은 화면의 스크린샷·URL을 주고 "이 느낌, 내 유저플로우대로". 맨땅에 "예쁘게"는 최악.
  2. Claude Design으로 화면 뽑기 — 슬라이더로 색·여백을 조정, 3버전 비교. 산출물은 프론트 코드 + 프로토타입.
  3. Claude Code로 이어 개발 — 그 코드를 내 프로젝트에 붙이고 "기능명세서대로 AI 요약을 붙이고 결과를 저장해줘".
📌 Design ↔ Code 전환 기준
"눈으로 보여야 할 땐 Design, 손으로 고쳐야 할 땐 Code."

1. 배포 3단계 — 로컬 → GitHub → Vercel

배포 = 내 컴퓨터의 폴더를, 24시간 켜져 있는 남의 컴퓨터에 올려 주소를 붙이는 것. GitHub는 작업물을 넣어두는 창고, Vercel은 창고를 보고 알아서 가게를 여는 점원입니다.

단계하는 일끝났다는 신호막히면
① 로컬 준비npm run build 통과 + .gitignore 확인Compiled successfully에러 전문을 Claude Code에 붙여넣기
② GitHubPrivate 레포 생성 + 첫 pushgithub.com에서 파일 보임공개(Public) 금지
③ VercelImport + 환경변수 + Deploy🟢 Ready + .vercel.app 주소Build Logs 마지막 빨간 줄
⚠ 90%가 여기서 넘어집니다
npm run dev가 되는 것과 npm run build가 되는 것은 다릅니다. 개발 모드는 에러를 봐주지만 빌드는 타입 에러 하나에도 멈춥니다. 올리기 전에 내 컴퓨터에서 build를 먼저 통과시키세요.
✏ 따라하기 — 매번 고칠 때의 3줄 (저장만으로는 아무것도 안 올라갑니다)
1git add . — 올릴 목록 담기 (먼저 git status로 .env.local이 없는지 확인)
2git commit -m "설명" — 봉인 + 메모
3git push — GitHub로 배송 → Vercel이 자동 감지 → 약 2분 뒤 사이트 갱신
💡 터미널이 무섭다면

2. 환경변수 이관 — 왜 화면은 뜨는데 기능만 죽나

환경변수 = 코드에 적으면 안 되는 비밀값(키)을 코드 밖에 따로 두는 것. 내 컴퓨터에서는 .env.local이 그 역할인데, 이 파일은 GitHub에 안 올라갑니다. 그래서 Vercel에는 키가 하나도 없는 상태로 코드만 올라갑니다. 비유: 가게는 옮겼는데 금고 열쇠를 집에 두고 온 것.

✏ 따라하기 — 키 옮기기
1내 .env.local을 열어 키 목록 확인
2Vercel → 프로젝트 → Settings → Environment Variables
3한 줄씩 추가 (비밀값은 Production + Preview 체크)
4비밀값(ANTHROPIC_API_KEY, SUPABASE_SERVICE_ROLE_KEY)은 Sensitive 토글 ON
5Deployments → Redeploy — 추가만 하면 반영 안 됩니다 (가장 흔한 실수)
🔴 이름 규칙 하나가 보안을 가릅니다 — NEXT_PUBLIC_
NEXT_PUBLIC_로 시작하는 변수는 브라우저에 그대로 노출(F12로 누구나 봄). 따라서 SUPABASE_SERVICE_ROLE_KEY에는 절대 붙이면 안 됩니다 — 이 키는 RLS를 우회해 DB 전체를 엽니다.
공개돼도 되는 것: SUPABASE_URL, ANON_KEY(RLS가 지키므로) / 공개되면 안 되는 것: ANTHROPIC_API_KEY, SERVICE_ROLE_KEY

6. 데이터베이스 — 엑셀로 생각하면 쉽습니다

테이블 = 시트 1장 · 컬럼 = 세로 항목 · 행(row) = 기록 1건. 기억은 재방문뿐 아니라 매출 근거입니다. 누가 몇 번 썼는지 모르면 가격도, 개선점도, 협상도 못 합니다.

스키마 설계 4단계 — 테이블부터 만들지 마세요

① 명사 뽑기→② 테이블로 승격→③ 컬럼 정하기 (5~8개)→④ 관계 잇기 (user_id)

"첫 테이블은 2개면 충분합니다. 5개 만들면 100% 다시 짭니다."

컬럼 5총사 (어떤 테이블에도)

컬럼역할빠뜨리면
id기록 1건의 고유 번호특정 행을 지목 불가
created_at언제 생겼나언제 뭐가 늘었는지 영영 모름 (소급 불가)
user_id누구 것인가RLS를 걸 수 없음 = 보안 불가
내용 컬럼실제 저장할 값—
status삭제 대신 상태 변경용실수로 지우면 복구 불가
💡 지우지 말고 "지운 척" (soft delete)
삭제 버튼은 행을 지우지 않고 status를 'deleted'로 바꾸고 화면에서만 숨깁니다 → 환불 분쟁 증거·통계·복구 유지. 단, 고객이 "내 정보 지워달라"고 하면 개인정보는 실제 삭제 또는 익명화해야 합니다.

RLS 필수 3단계와 자가 테스트

  1. 모든 테이블 RLS Enable (처음부터 켜고 개발)
  2. 정책 최소 2개 — SELECT·INSERT (auth.uid() = user_id)
  3. 다른 계정으로 테스트 — 시크릿 창에서 다른 계정으로 로그인해 내 데이터가 안 보이는지, 응답이 빈 배열 []인지 확인
⛔ 절대 금지
FOR ALL USING (true) = "전부 허용". 예제 코드에 자주 나오니 조심. 5-1에서 저장이 안 되던 이유는 로그인이 없어 auth.uid()가 비어(NULL) 모든 접근이 거부됐기 때문입니다.

로그인 없이 저장하고 싶다면 — 익명 저장 스키마

🅰 로그인 있음 (analyses)🅱 로그인 없음 (submissions)
user_id필수없음
넣기본인 것만누구나 (접수)
읽기본인 것만아무도 못 읽음 (나만 대시보드·관리자에서)
쓰는 곳마이페이지·히스토리문의 접수·무료 진단·생성기

🅱에서 읽기까지 열면 남의 연락처를 전부 볼 수 있습니다 (개인정보 사고 1순위).

7. OAuth 로그인 — 비밀번호를 들고 가지 마세요

직접 비밀번호를 관리하면 암호화·재설정·분실 대응과 유출 시 법적 책임이 따릅니다. OAuth(카카오·구글·네이버 로그인)를 쓰면 비밀번호는 그쪽 금고에 있고, 내 DB에는 user_id와 이메일만 남습니다. 일반 대중 대상이면 카카오 > 네이버 > 구글, B2B·개발자 대상이면 구글 > 네이버 > 카카오.

✏ 카카오 OAuth 연결 순서
1카카오 개발자 사이트에서 애플리케이션 추가
2제품 설정 → 카카오 로그인 → 활성화 ON (안 켜면 아래를 다 해도 실패)
3보안 → Client Secret 발급 + 상태 '사용함'
4Redirect URI 등록 — Supabase 화면에 표시된 Callback URL을 복사해서 그대로 붙여넣기
5Supabase → Authentication → Providers → Kakao 활성화 + REST API 키·Secret 입력
6프론트에서 signInWithOAuth({ provider: 'kakao' }) 호출 (AI에게 시키면 됨)

실패 1순위 = Redirect URI 오타 (redirect_uri_mismatch 에러). 한 글자만 달라도 실패하므로 손으로 타이핑 금지.

8. 보안 4대 방어선 — 공개된 순간 4개가 동시에 필요

방어선지키는 것핵심
① 결제 Webhook 3중 방어돈결제를 붙이는 사람만. 결제사에 재조회 + 금액·주문번호 일치 검증 + 결제키 UNIQUE 제약 (가짜 결제 1줄로 만들 수 있음)
② SERVICE_ROLE 키 격리데이터서버 전용 파일에서만 사용, Sensitive ON, NEXT_PUBLIC_ 금지, 커밋 금지
③ Rate Limit비용일반 API는 IP당 분당 60회, AI 호출은 IP당 하루 10회. 봇은 61번째부터 차단(429)
④ 배포 검증 6가지신뢰"됐다"고 알렸는데 안 되는 조용한 실패 방지. 결과를 기다리지 않는 void (async…) 패턴 금지(await 사용)
🛡 공개 전 최종 보안 5분 체크
① .env.local이 GitHub 이력에 없다 ② SERVICE_ROLE 키가 프론트 코드에 없다 ③ 모든 테이블 RLS Enable + 정책 존재 ④ 다른 계정으로 로그인해 남의 데이터가 안 보인다 ⑤ AI 호출에 max_tokens + 입력 제한 + Rate Limit
